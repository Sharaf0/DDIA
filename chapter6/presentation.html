Section 6.2

Partitioning of Key-Value Data

Key range vs hash, compound keys, and fighting skewed hot spots

The Goal vs The Enemy vs Naive Random

6.2.1 Key Range

Partitioning by Key Range

Assign a continuous range of keys (min → max) to each partition — just like volumes of a print encyclopedia.

  • Boundaries adapt to data skew (Vol 1: A–B, Vol 12: T–Z)
  • Inside each partition, keys stay sorted (SSTables / LSM-Trees)
  • Range scans & concatenated indexes are super fast

Used by: Bigtable HBase RethinkDB MongoDB <2.4

The Key-Range Trap: Time-Series Hot Spots

If your key is a timestamp (YYYY-MM-DD-HH:MM:SS), range scans for "last month" are trivial — but all live writes hit today's partition!

Fixing Timestamp Skew: Prefix With Sensor Name

❌ Raw Timestamp Key

key = "2026-11-23-04:15:01"
  • Writes: 100% slam today's partition
  • Read all sensors for Nov: 1 single range scan

✅ Sensor-Prefixed Key

key = "sensor_42/2026-11-23-04:15:01"
  • Writes: Spread evenly across all sensor partitions
  • Read Trade-Off: Querying 50 sensors over a time range now requires 50 separate range queries
Key Insight: Partitioning first by sensor_name and second by timestamp removes the write bottleneck, at the cost of per-sensor read queries.
6.2.2 Hash of Key

Partitioning by Hash of Key

Feed the key into a deterministic hash function → assign ranges of hashes to each partition.

  • Similar timestamps (17:08:10, 17:08:11) hash to wildly different numbers → uniform spread
  • Need not be cryptographic: MD5 (MongoDB) Murmur3 (Cassandra) FNV (Voldemort)
  • Ranges can be evenly spaced, or chosen pseudorandomly

Two Subtle Traps in Hash Partitioning

❌ Trap 1: Built-In Language Hashes

Java Object.hashCode() & Ruby Object#hash can differ across processes/restarts!

⚠️ Trap 2: "Consistent Hashing" Confusion

  • Coined by Karger et al. (1997) for CDNs/caches with randomly chosen ring boundaries to avoid central control.
  • Nothing to do with Ch. 5 replica consistency or ACID consistency!
  • Actually works poorly for databases (unbalanced splits), so real DBs use fixed/dynamic hash ranges instead.
  • Kleppmann's advice: Just say hash partitioning.

The Price of Hashing: Range Queries Break

Adjacent keys that lived side-by-side are now scattered across every partition — sort order is destroyed.

Best of Both Worlds: Cassandra's Compound Key

Hash the first column to choose the partition; keep remaining columns sorted inside the partition's SSTable.

user_42 | 2026-11-23 09:00 → "Morning!" user_42 | 2026-11-23 11:30 → "Coffee time" ✅ Ideal 1-to-many model (user → timeline posts)

6.2.3 Skewed Workloads Even Hashing Can't Save You From One Hot Key

Hashing distributes distinct keys evenly — but if millions of users comment on the exact same celebrity key, all traffic hashes to the same partition.

Section 6.3

Partitioning & Secondary Indexes

When queries search by values instead of primary keys

Why Secondary Indexes Complicate Partitioning

A secondary index (color:red, user:123, word hogwash) doesn't identify one unique record — matching items can live in any partition.

HBase & Voldemort avoided secondary indexes; Riak, MongoDB, Cassandra, Elasticsearch, DynamoDB tackle them in two ways.

6.3.1 Local Index

Partitioning by Document

Each partition maintains its own secondary index covering only the documents stored inside that partition.

  • ✅ Writes: Fast & local — only touch the single partition owning that document ID
  • ❌ Reads: Must scatter/gather across every partition and merge results
  • Used by: MongoDB Riak Cassandra Elasticsearch SolrCloud VoltDB

The Hidden Danger of Scatter/Gather: Tail Latency Amplification

Even when querying all partitions in parallel, the user waits for the slowest partition to respond.

6.3.2 Global Index

Partitioning by Term

Construct a global index covering all data, then partition that index by the indexed term (e.g., color:a–r vs s–z).

  • ✅ Reads: Query one index partition directly (no scatter/gather!). Can range-scan terms or hash terms for balance.
  • ❌ Writes: Writing 1 document can touch multiple partitions (data + color shard + make shard)
  • Used by: DynamoDB GSI Riak Search Oracle DW

Global Index Dilemma: 2PC vs Async Lag (Plus DIY Trap)

Footnote (ii) Warning — DIY App-Level Indexes: If your KV store lacks secondary indexes and you maintain them yourself in app code, race conditions & partial write failures easily leave indexes permanently out of sync with data!

Section 6.4

Rebalancing Partitions

Moving load cleanly as hardware scales, shrinks, or fails

Why Rebalance & The 3 Non-Negotiable Rules

Triggers for Rebalancing

  • 📈 More traffic: Add CPUs to handle higher QPS
  • 💾 More data: Add disks & RAM for storage
  • 💥 Node failure: Surviving nodes take over

3 Minimum Requirements

  • ⚖️ Fair share: Storage & QPS balanced afterward
  • 🔄 Zero downtime: Reads/writes keep working during move
  • 📦 Minimal transfer: Move only necessary bytes (save network & disk I/O)

6.4.1 Strategies How NOT to Do It: hash(key) mod N

Changing the node count N changes the remainder for almost every key, triggering a massive network storm.

Strategy 1: Fixed Number of Partitions

Create many more partitions than nodes upfront (e.g., 1,000 partitions across 10 nodes = ~100/node).

  • When a new node joins, it steals whole partitions from existing nodes
  • Key-to-partition mapping never changes — only partition-to-node ownership changes
  • Old assignment serves reads/writes while bulk data copies in the background
  • Supports mismatched hardware (assign more partitions to beefier nodes)

Used by: Riak Elasticsearch Couchbase Voldemort

The Fixed-Partition "Goldilocks" Dilemma

Because partition count is fixed at cluster creation (hard/impossible to change later), picking the right number is tricky:

Too Few Partitions

  • Caps maximum nodes (cannot exceed partition count)
  • Each partition grows huge as data grows
  • Rebalancing & node recovery become painfully slow

🎯 "Just Right"

  • Matches expected future dataset size
  • Fast recovery & fine-grained load balancing
  • Hard to predict if data grows 100× over 5 years!

Too Many Partitions

  • Per-partition management & metadata overhead
  • Each partition tracks files, Raft/Paxos groups, or indexes
  • Too small = wasted coordination overhead

Strategy 2: Dynamic Partitioning (Split & Merge)

Partitions grow and shrink automatically with data volume — like the top level of a B-Tree.

The Dynamic Caveat: Empty DB Bottleneck & Pre-Splitting

❌ Cold-Start Problem

An empty DB has no key distribution yet — so it starts with 1 partition on 1 node.

✅ Pre-Splitting Solution

Configure initial split boundaries on the empty database (supported by HBase & MongoDB).

Strategy 3: Proportional to Nodes (Cassandra vNodes)

Instead of fixed total partitions or fixed data size, keep a fixed number of partitions per node (e.g., Cassandra default: 256 vnodes/node).

  • Partitions shrink as you add nodes — keeping partition sizes stable as cluster scales
  • Requires hash partitioning (boundaries drawn from hash space — closest to Karger's consistent hashing)
  • Random splits can be uneven, so Cassandra uses 256 vnodes/node (improved in Cassandra 3.0 token allocation)
  • Used by: Cassandra Ketama

Section 6.5

Request Routing

Service discovery for databases & parallel query execution

The Core Question: "Which IP & Port Owns Key foo?"

Once partitions rebalance across nodes, partition-to-IP mappings constantly evolve — this is a specialized case of service discovery.

Why It's Harder Than Stateless APIs

  • A stateless web request can hit any replica
  • A partitioned write/read for "Danube" MUST reach the exact node currently owning partition 2
  • If participants disagree on the mapping → requests route to wrong nodes!

DNS Alone Isn't Enough

  • DNS is fine for finding slow-changing cluster IPs (load balancers / routing tier)
  • DNS TTL caching is far too slow for rapid partition reassignments
  • Requires consensus or gossip for partition metadata

Three Ways to Route a Request

  1. Contact any node — via round-robin LB; if wrong node, it forwards internally to the owner
  2. Routing tier — partition-aware load balancer handles routing, nodes stay dumb
  3. Smart client — client caches the partition→node map and connects directly (zero extra hops)
In all 3 cases, the hardest question is identical: how does the router stay updated when partitions move?

ZooKeeper: Authoritative Cluster Metadata

Many systems offload consensus to a dedicated coordination service like ZooKeeper.

  • Each DB node registers its owned partitions in ZooKeeper
  • Routing tier / smart clients subscribe (watch) for changes
  • Partition moves → ZooKeeper notifies watchers instantly
  • Examples: HBase Kafka SolrCloud LinkedIn Espresso (Helix)
  • MongoDB uses its own config servers + mongos routers

Coordination Showdown: ZooKeeper vs Gossip Protocol

🧭 External Consensus (ZooKeeper)

  • How: Single authoritative source of truth via consensus (Ch. 9)
  • Pros: Strong agreement — routing tier has consistent view
  • Cons: Extra operational dependency to run & monitor
  • Systems: HBase, Kafka, SolrCloud, Espresso, MongoDB (config server)

💬 Peer-to-Peer Gossip Protocol

  • How: Nodes exchange cluster state updates directly with peers (Approach 1 forwarding)
  • Pros: Zero external service dependency
  • Cons: More complexity inside DB nodes; brief stale views during propagation
  • Systems: Cassandra Riak (plus Couchbase moxi via cluster nodes)
